# Dataset testing

Ten datasets, nine downloaded in full from public GitHub copies and one generated with a fixed seed. Each has a manifest (`datasets/manifests/`) with its URL and SHA-256, and a rules file (`configs/datasets/`) written for that dataset's meaning.

`scripts/verify_datasets.py` audits each file and compares the result with a reference that re-reads the file with the standard-library `csv` module and recounts everything: rows, columns, exact duplicate rows, missing cells per column, numeric min/max per column, duplicate keys, and every configured rule. The reference does not import the auditor's checking code. Results are saved to [verification_results.json](verification_results.json).

To confirm the check can fail, whitespace-only cells were temporarily treated as present in `checks/missing.py`. The verifier reported `telco_churn: missing[TotalCharges]: auditor=0 reference=11` and exited non-zero. The change was then reverted.

## What each dataset tested, and what it found

**Titanic.** Missing values in Age (177), Cabin (687) and Embarked (2). Before this release none of them raised an issue, because only `required` columns did; see the changelog. Age has values like `0.42` and `28.5`, and was inferred as `integer` before the int/float fix.

**Iris.** A clean baseline. The one duplicate row is a known property of the dataset, not a parser artefact.

**Telco churn.** `TotalCharges` holds a single space for 11 customers with zero tenure. With `whitespace_as_missing: true` these count as missing, not as invalid floats. `customerID` is unique and masked in reports.

**Ames housing.** The file was saved by pandas with its index, so the first header is blank. The auditor used to stop with an error; it now names the column `unnamed_0` and raises a medium issue. One row fails `Yr Sold >= Year Built` (sold 2007, built 2008), which may be a pre-construction sale rather than an error. Many "missing" cells (Alley 93%, Pool QC) mean "this house has none" in the Ames data dictionary, so a high missing rate here is a question for the data owner, not proof of bad data.

**Apple stock.** Daily prices with a `high_ge_low` cross-column rule and unique dates. Nothing should be flagged and nothing is.

**Pima diabetes.** No header row (`--no-header --columns ...`). Missing readings are stored as `0`, which the auditor treats as valid by default. Rules `min: 1` on glucose, blood pressure and BMI catch them: 5, 35 and 11 rows. This is the point of configurable rules: `0` is only wrong if you say so.

**Diamonds.** 54k rows with quoted fields. 146 exact duplicate rows; 8, 7 and 20 diamonds have `x`, `y` or `z` of zero.

**Seattle weather.** Negative minimum temperatures are valid, so no `min` rule is set on them. `temp_max >= temp_min` holds on every day.

**Earthquakes (1965-2016).** Latitude, longitude and magnitude are all in range. Three rows (1975, 1985, 2011) use `1975-02-23T02:58:41.000Z` instead of `MM/DD/YYYY`. The two duplicate rows are same-day events at the same rounded location; this copy has no time column, so they may be separate earthquakes.

**Synthetic.** Generated by `scripts/generate_synthetic.py` with seed 42 and a ground-truth file. The verifier also checks the auditor against that file: 1 cross-chunk duplicate (row 10 and row 50,015), 2,098 negative amounts, 993 invalid dates, 4,879 missing notes. All match.
